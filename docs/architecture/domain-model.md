# Domain model

A realm is an authentication security partition; it is not a workspace/business organization. A registered client belongs to a realm and has exact redirects, origin policy and audience. The first slice binds one realm per server/router in trusted configuration; no request body may select it.

User has opaque random UUID, realm, verified email and lifecycle status. Email policy initially supports a conservative ASCII mailbox and canonicalizes case consistently; no plus/dot rewriting. This product policy can conflate case-sensitive local parts and must be explicit. Email change now requires a fresh session and separate confirmation of both current and proposed mailboxes, preserves the user ID and revokes sessions. ExternalIdentity is unique by (realm, connection, trusted issuer, subject); matching emails never merge users. Linking proves current fresh session and a new provider transaction. Unlinking cannot remove the last usable credential/recovery path. Merges are disabled until separately reviewed.

Password credentials now store a salted Argon2id PHC string under a realm/user composite key, with single-enrollment uniqueness. Enrollment requires a fresh verified session and replaces existing sessions atomically. Passkey credentials remain planned. Credentials (password, passkey) are distinct from provider accounts and user records. Passkey stores RP-scoped credential/public-key state, counter, UV/backup metadata and a user label. Discoverable enrollment provisions a passkey-first user under a verified enrollment transaction. Recovery cannot silently replace stronger assurance with email; explicit policy, delays/notifications and audit required.

AuthenticationTransaction carries realm/client/connection, purpose, browser binding, state/nonce/PKCE verifier and expiry. VerificationChallenge holds only token/browser verifiers, email/purpose and expiry. Consume atomically in the transaction that creates the user and session. A failed session insert rolls back consumption. Password-reset proofs use a separate table/cookie and bind the current credential version; consumption, password/version update, session/proof invalidation, audit and non-secret notification enqueue commit atomically. Delivery claims are leased and realm scoped. Parallel consumption yields one winner. PostgreSQL constraints include realm in all identity relations.

Session holds a public opaque ID, user+realm composite FK, SHA-256 verifier of a random 256-bit secret, created/last-seen/absolute expiry and revocation state. Browser receives the secret only in HttpOnly cookie. Lookup validates idle and absolute limits in the same database operation. Revocation takes effect on the next database validation; already-authorized in-flight operations can complete. Sensitive operations use separate authenticated_at provenance; rotation does not reset it. Legacy sessions require fresh sign-in after migration 0004. Application-specific transaction semantics remain the consumer’s responsibility.

Refresh/token families are separate future native/OAuth entities: short access lifetimes, atomic refresh rotation, family replay detection and OS secure storage. JWT expiration is not revocation. SigningKey records public metadata and protected key reference; never put plaintext private keys into logs/config dumps. AuditEvent contains bounded event kinds and opaque subjects, not payloads, tokens or email addresses.

Planned entities are not implemented tables until their milestone. Account deletion now transactionally removes implemented credentials/sessions/proofs and deidentifies live audit subjects; future external identities must join this same lifecycle. A subject-free deletion notice temporarily retains the established recipient for delivery.
