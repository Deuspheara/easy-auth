# ADR 0007: Typed lifecycle facts and explicit linking proof policy

Status: accepted for alpha, AUTH-16, 2026-10-19.

Audit writes use the core's closed `AuditEvent` variants and a private PostgreSQL transaction writer. Their payload contains only opaque UUID references, a fixed kind/version and database time. There is no arbitrary context, claims object, email, credential/verifier, provider token or raw request field, and no generic append API. Events describe successful committed facts; an attempted operation that rolls back must not leave a success event.

Version 1 records distinguish the owned user, initiating session where applicable, and issued/affected session where applicable. Composite foreign keys enforce the configured realm and shared owner. Recovery is authorized by its version-bound proof, not a fabricated session actor. Ordinary logout can revoke an expired owned session; an actor reference alone does not assert freshness. Sensitive management operations still perform the existing freshness checks under locks.

The user lock precedes session mutations and audit-reference checks. Logout joins this ordering to avoid a session-lock/user-lock inversion introduced by the new foreign keys. Database lock-barrier tests cover that ordering and verify that event time reflects recording after the wait rather than transaction start. Lifecycle mutation, audit write and any notification enqueue share one transaction. Deletion erases user/actor/target references from the subject's complete live audit history before deleting its user/sessions and adding a subject-free deletion fact; unrelated subjects are unchanged.

Migration 0006 preserves existing rows as version 0 with unknown actor/target attribution. It does not guess historical session references. Dangling/cross-realm subject references and old deletion facts are deidentified. New runtime writes explicitly use version 1; older binaries cannot keep appending incomplete default-version rows. This alpha requires coordinated upgrades rather than mixed-version writers. Historical-version support is not a security boundary against a privileged database writer.

Account linking is a distinct future operation, implemented with its provider flow in AUTH-25. Its mandatory proof contract is: a fresh current-account authentication plus a separate purpose/realm/connection/browser-bound transaction proving the new trusted issuer/subject. Revalidate both controls and external-identity ownership under locks at commit. Equal email, even verified email, is never ownership proof or merge authority. A new identity already owned by another user is rejected; there is no implicit reassignment or account merge. Unlinking must preserve a usable authentication/recovery path under the eventual factor policy.

A successful future link/unlink must commit its identity mutation and a specifically typed audit event together, using bounded owned references and no provider claims/tokens. The event enum/schema must be extended with that implementation and its negative/rollback tests. No linking-success kind or endpoint is enabled now. The implemented two-mailbox email-change flow preserves one user's ID; it does not link or merge users and does not establish provider interoperability.

Alternatives rejected: generic JSON audit payloads (accidental secret/PII retention), out-of-transaction success logs (false evidence on rollback), matching-email linking (account takeover), and guessed historical actor IDs (false attribution). Bounded schema does not bound total row count. Retention, privileged read/export access, tamper resistance and independent review remain explicit operational release work; session pruning must account for audit foreign-key references.
