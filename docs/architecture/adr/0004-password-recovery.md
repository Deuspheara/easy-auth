# ADR 0004: Purpose-bound password recovery and durable notices

Status: accepted for alpha, AUTH-13, 2026-10-18.

Use a separate password-reset proof table and cookie, with the existing 256-bit random secret/verifier scheme. Start stores a proof and sends the same template to every normalized email, including unknown and email-only accounts. Only a proof bound to an existing current password credential version can complete. This keeps start's response and delivery path independent of account existence without allowing reset to enroll a password or create a user.

Finish checks proof/browser/realm/expiry before bounded Argon2 work, then rechecks under the transaction's locks. The transaction changes the password and credential version, revokes sessions, deletes outstanding reset and email sign-in proofs, records an audit event and queues a non-secret notice. No automatic sign-in follows recovery. Proof and password change roll back together on any persistence failure.

Proof issuance, email sign-in consumption and reset take a PostgreSQL transaction advisory lock keyed by realm plus normalized email. The database hash only selects a lock; it is not used for cryptography. Collisions can serialize unrelated requests but do not authorize them. This common lock precedes user/credential/session locks and ensures proof issuance cannot slip across reset invalidation. Password enrollment/login retain their user-row lock; future credential/email changes must preserve this order and recheck credentials after locking.

SMTP cannot commit atomically with PostgreSQL. A dedicated notification table contains only event/user identifiers, established recipient and retry state, never a password, hash or proof. A single bounded worker per composition claims with SKIP LOCKED and a renewable-by-reclaim 30-second lease. SMTP is bounded to ten seconds. Delivery is at least once, so cancellation or an ambiguous SMTP result can cause duplicates. Eight failed/abandoned claims exhaust automatic retries; failed rows remain for explicit operator inspection/redrive. No generic event bus, encrypted proof outbox or new service dependency is introduced.

Alternatives: synchronous post-commit notification can falsely report reset failure after the credential has changed; sending before commit can notify about a reset that rolled back. A database-backed non-secret notice makes the actual change authoritative and notification recoverable. Tradeoffs are a worker, operational queue monitoring/retention and possible duplicate notices. Sending reset-request mail to unknown accounts has a rate-limited mail-abuse cost. Mailbox recovery remains the same alpha assurance model as existing email sign-in; it is not an approved recovery path for future stronger-factor accounts.
