# Ecosystem review

Reviewed 2026-10-18, with the AUTH-5 maintenance correction and [native integration measurements](adoption-comparison.md) on 2026-10-19. Public default-branch shallow clones were inspected; exact revisions and commit timestamps are in [source-snapshots.json](source-snapshots.json). This is a targeted design review, not a security audit. Full upstream test suites were not run; AUTH-5 compiled and exercised the explicitly documented native session probes. Source links below are pinned to inspected commits. Feature presence means code was found, not independent conformance certification.

## Community, maturity and security evidence

The snapshot timestamps establish recent commits, not ongoing maintenance, response-time guarantees, governance health or a bus-factor assessment. In particular, [RustAuth's pinned README](https://github.com/salasebas/rustauth/blob/b55e9ce3c9f375a66d8ae7ef40afe0cbd041ec1e/README.md) explicitly declares it unmaintained, with no further releases, bug fixes or security updates planned. Its final commit is the maintenance notice itself. The initial comparison missed this notice; RustAuth remains a historical baseline and possible community-fork reference, not an actively supported adoption recommendation. Better Auth has a much larger visible contributor/user surface than the Rust compatibility projects; stars are not security evidence. RustAuth and lucid-auth expose broad tests but remain pre-1.0 here; Better Auth RS is explicitly alpha. Rauthy, Kanidm and Kratos have established service-oriented histories. None of these observations constitutes an audit endorsement.

[Better Auth's June 2026 security update](https://better-auth.com/blog/security-update-june-2026) records OAuth code-redemption and plugin fixes. [Kanidm release notes](https://github.com/kanidm/kanidm/releases) include an origin-matching correction in the WebAuthn ecosystem. These illustrate the need for negative tests, timely dependency updates and coordinated disclosure. The [2026-10-27 published advisory inventory](advisory-history-2026-10-27.md) maps all 52 observed repository advisories and 74 package ranges to these seven pins. One Better Auth range matches; Kanidm development-pin applicability remains unresolved. Empty feeds and version labels establish no vulnerability clearance; complete transitive/native and exact-fix assessments remain adoption prerequisites. Measure resolved dependency graphs and binary/RSS under the same feature set before making footprint comparisons; manifest breadth is only a qualitative proxy.

## Product scope and reuse strategy

1. RustAuth and Better Auth RS already solve much of embedded authentication. Our proposed distinction is a deliberately small PostgreSQL-first product with an independent versioned contract, one shared embedded/service use-case layer, tenant-scoped verifier storage, and immediate server-side revocation. This is a hypothesis to prove through a working integration, not a novel-protocol claim.
2. Reuse webauthn-rs, openidconnect/oauth2, RustCrypto Argon2/SHA-256, SQLx, Axum, lettre and established XML signature engines. Reuse ideas and test strategies; no upstream authentication implementation is copied. RustAuth/lucid-auth compatibility is neither promised nor needed.
3. Contributing is likely safer for teams that need Better Auth compatibility or an operational issuer now. Contribute protocol-negative-test fixtures or library fixes upstream. Proceed with a small independent project because the requested two-mode SQLx-focused contract differs; stop expanding if a contributor evaluation demonstrates equal ergonomics and security with less maintenance.
4. Earn adoption with a five-minute reproducible setup, identical embedded/service behavior, inspectable SQL migrations, explicit trust policies, release-gated conformance, no enterprise paywall, and measured footprint. Avoid a plugin engine and application authorization features.
5. Smallest valuable slice: browser-bound email proof, transactional user creation, opaque server-side sessions, protected Axum route and logout on real PostgreSQL with local SMTP. Passwords, passkeys, federation and outbound issuer remain separately gated milestones.

See [ADR 0001](../architecture/adr/0001-build-versus-contribute.md). Read the provider and dependency assessment before changing protocol behavior.
